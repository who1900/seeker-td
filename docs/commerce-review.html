Fixed finding — High / correctness and payment safety

src/services/commerce.ts → createCommerceClient().purchase(). Previously, only the same quote ID was blocked; a new quote for the same UID/payer could broadcast while an earlier payment outcome was unknown. Offline reproduction produced two broadcasts and two late server grants.

Fix: assertCommercePurchaseAllowed() runs before the signing transport and again in the synchronous beforeBroadcast journal boundary. Unknown same-scope entries block new intents; every previously signed quote remains blocked, including confirmed quotes. Different UID/payer scopes remain isolated.

PendingCommercePurchase.confirmedReceipt is optional in the unchanged v1 journal. readCommercePending() validates its closed seven-field shape and binds receipt ID/status, quote ID, signature, payer and exact grants. acknowledgeCommerceReceipt() persists only a validated server response and checks the complete journal readback before returning the receipt for cache application.

A confirmed acknowledgement permits a different purchase intent, not authorization or a grant. pending() retains all entries; reconcile() still contacts the server. Failed/dropped acknowledgement writes fail closed. No unknown or confirmed history is pruned; the 256-entry capacity is preserved and checked before signing. Old entries without acknowledgement remain unknown until reconciled.
